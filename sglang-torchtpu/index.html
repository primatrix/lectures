同一个问题：设备内存由谁管理

JAX 路线的成本不在性能，在控制面

为什么最后选择重写框架

  1. 设备抽象不同。JAX 用全局数组加 mesh / sharding 描述设备；PyTorch 用 torch.Tensor 加 device module 直接分配。
  2. 调度恰恰依赖这套 API。最核心的是基于 KV cache 的请求管理：容量、槽位和生命周期都在操作设备内存。
  3. 于是只能重写。大部分 Schedule 代码要按 JAX 的设备模型重写，所以选择重写框架，而不是移植调度。

TorchTPU 换来了什么

torch.Tensor + eagermodeling 仍是 nn.Module，可以照常运行和调试
torch.compile(backend="tpu")执行仍交给 XLA 编译，不改变模型写法
torch.distributed并行与通信接口不变，沿用 upstream 的并行层

三件事合起来：TPU 只是一个普通的 PyTorch device。

因此 SGLang 的 modeling 定义、调度器与 API Server 可以不改 API 复用；选择的依据是复用，不是两条路线的性能比较。

从 JAX 到 Torch · 分片与通信的表达方式

从全局数组，走到每个 rank 的局部程序

熟悉的 JAX 全局数组路径

全局 Array + mesh / sharding
描述全局运算与目标布局
编译器推导局部计算与所需通信

当前 SGLang-TorchTPU 主路径

每个 rank 持有局部 torch.Tensor
并行层定义局部计算与 collective
TorchTPU / XLA 编译这些操作
两边最后都落到 JAX / Pallas kernel

JAX 侧直接写；TorchTPU 侧通过 jax_op 包一层再调，kernel 体内仍是同一套 JAX / Pallas API。

@pl.pallas_call(out_shape=…, grid=(…),
                in_specs=…, out_specs=…)
def kernel(x_ref, w_ref, o_ref):
    o_ref[...] = jnp.dot(x_ref[...], w_ref[...])
跨设备分片与 collective 由并行层定义；单设备计算仍交给 XLA / Pallas kernel。

与 SGLang GPU 常规 TP 沿用相同的局部分片思路；TPU 的显式通信继续进入 XLA 编译链。
